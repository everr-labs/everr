title: Set up alert notifications
description: Route firing and resolved alerts to receivers with matchers, and control grouping, repeats, silences, and inhibitions.
---

Alert rules are defined as code, but delivery is configured in the app and applies across the whole organization. Everything below lives under **Alerts** in Everr: channels, receivers, and routes on the **Delivery** page, silences on the **Silences** page.

## The delivery pipeline

When an alert fires or resolves, it walks a fixed path:

1. **Routes** are checked top to bottom by priority; the first route whose matchers fit the alert's labels decides the receiver.
2. The matched **receiver** fans the notification out to every **channel** it references (Slack, Discord, email, webhook, or Telegram).
3. An alert that matches no route is **not delivered**, so end the route list with a catch-all (a route with no matchers) if you want a default receiver.

Silences and inhibitions suppress delivery without stopping evaluation.

## Channels

A channel is a named delivery endpoint, created and deleted on the Delivery page. Channels are reusable: any number of receivers can reference the same channel by name.

Channel types: **email** (recipient addresses), **Slack** (an [Incoming Webhook](https://api.slack.com/messaging/webhooks) URL), **Discord** (a [channel webhook](https://support.discord.com/hc/en-us/articles/228383668) URL), **webhook** (any HTTPS endpoint), and **Telegram** (a bot token and chat IDs, see Telegram's [BotFather guide](https://core.telegram.org/bots/features#botfather)).

Webhook URLs (generic, Slack, and Discord) and Telegram bot tokens are write-only: after saving, Everr shows them redacted (`***`). Email recipients are not secrets and stay visible as entered. To rotate a redacted secret, edit the channel and enter the new value; the secret fields start blank on edit precisely because the stored values are never shown again. Names are editable labels: renaming a channel or receiver never breaks the receivers and routes that reference it.

A channel that is still referenced cannot be deleted: Everr surfaces the engine's refusal, naming the receivers that still use it. Delete or repoint those receivers first.

## Receivers

A receiver is a named set of channels; routes reference receivers by name, and a notification for the receiver is delivered to every channel in the set. Create a receiver on the Delivery page by picking from your existing channels (at least one). Receivers carry no secrets themselves, only channel names.

## Routes

A route is a set of **matchers** (label comparisons such as `severity = critical`, with equals, not-equals, and regex operators), a target receiver, and a priority. Routes are checked in priority order and the first match wins.

### Group notifications

Grouping happens after a route selects a receiver. It does not change which alerts fire or where they are sent. It decides which alert instances are batched into the same Slack message, email, or webhook payload.

For example, if 20 pods trigger the same rule during the group-wait window, grouping them by rule and severity produces one notification containing 20 instances instead of 20 separate notifications.

The route editor offers three grouping modes:

| Mode | Behavior |
| --- | --- |
| **Automatic** | For alert rules, groups by rule and severity. For SLOs, groups by SLO while combining its burn-rate tiers. This is the recommended starting point. |
| **One group** | Puts every alert sent to this receiver into one notification group. This can be useful for a receiver dedicated to one incident stream, but it can mix unrelated alerts. |
| **By labels** | Creates one group for each combination of selected label values. Grouping by `cluster`, for example, produces a separate notification stream for each cluster. |

Groups are always separate per receiver. Choosing **One group** combines alerts for one receiver, not across every receiver in the organization.

Choose labels that match how responders divide incidents. Labels such as `service`, `cluster`, `region`, or `team` are often useful. Too few labels can combine unrelated incidents; too many labels can fragment one incident into many notifications and defeat batching. Avoid grouping by `status`, particularly when repeat notifications are enabled, because firing and resolved events can land in different groups.

### Control notification timing

Each route also controls when its groups are sent:

- **Group wait** holds a new group before its first send so a burst can become one notification. It is also the minimum delivery delay for a newly created group.
- **Group interval** is the minimum time between updates for a group that has already been sent.
- **Repeat interval** re-sends a group while it still contains firing alerts, so a long-lived incident is not silent after its first notification. Leave it empty to notify only when the group's contents change.

## Inhibitions

An inhibition suppresses downstream alerts while a related, higher-level alert is already firing: while alerts matching the **source** matchers fire, alerts matching the **target** matchers are suppressed. Optional **equal labels** scope it to pairs that share the same value for those labels, so a database outage in `region=eu` only inhibits alerts from the same region.

## Silences

To stop notifications for a known issue or maintenance window without touching the rule, create a **silence** on the Silences page: matchers select the alerts, a time window bounds the suppression, and a comment records why. Silences can be scheduled ahead of a maintenance window. The rule keeps evaluating the whole time; silenced alerts are suppressed from delivery and recorded in the event stream.

For when notifications fire, see [How alerts work](/docs/concepts/how-alerts-work).
