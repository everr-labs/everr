This is step 5 of getting started with Everr: write one rule, reconcile it with `everr apply`, and open it in the Alerts UI. Apply uses your `everr cloud login` session; for CI or non-interactive use, set `EVERR_API_KEY` to a key with the **Manage as code** capability (see the [`everr apply` reference](/docs/reference/cli)). The example alerts on Node.js runtime metrics; swap the query for a signal your own services emit.

## Let your Agent pick a starter

The hard part of a first alert is knowing what to alert on. Everr ships the `everr-setup-resources` skill; run this from the repository that emits the telemetry:

```text
/everr-setup-resources Help me build a good first alert based on the telemetry we have in production
```

The Agent picks the signal, sets a threshold from your real baselines, writes the rule, and stages it in a preview. Make sure it's actionable: fire on symptoms users feel, not causes.

## Alternative: write it by hand

The rest of this step is the same workflow done manually. If you already created an `everr/` directory in the previous step, reuse it: apply discovers and reconciles everything under it, and alerts (`*.alert.yaml`) sit flat alongside dashboards.

Apply scopes everything to your repository's identity (its `repoid`), inferred from the repo's `origin` remote as `host/owner/repo`. Nothing to configure.

## Write the rule

`everr/eventloop-delay.alert.yaml`:

```yaml
kind: AlertRule
metadata:
  name: eventloop-delay
spec:
  display:
    name: Node.js event loop delay
    description: Services whose event loop is blocked over the last 5 minutes.
  evaluationInterval: 1m
  notificationMessage:
    title: "${ServiceName} event loop is lagging"
    description: "p99 event loop delay averaged ${value}ms over the last 5 minutes"
  condition:
    operator: gt
    threshold: 100
  query: |
    SELECT
      ServiceName,
      round(avg(Value) * 1000, 1) AS value
    FROM metrics_gauge
    WHERE MetricName = 'nodejs.eventloop.delay.p99'
      AND TimeUnix >= now() - INTERVAL 5 MINUTE
    GROUP BY ServiceName
    ORDER BY value DESC
```

A few things worth noting:

- `metadata.name` is the rule's **slug** and identity. Use lowercase letters, digits, and hyphens.
- The query returns one row per service, including healthy services, with the measured signal aliased to the required numeric `value` column. `condition` fires only rows above 100ms. This lets the same query display useful data when no alert is firing. `nodejs.eventloop.delay.p99` is reported in seconds, so the query converts it to milliseconds. Tune the threshold to your services. Averaging over the 5-minute window keeps a single momentary blip from paging.
- `ServiceName` is a string column, so Everr uses it as each instance's identity automatically: one alert instance per service.
- `notificationMessage` is templated with `${ServiceName}` and `${value}` from that instance's row; only columns the query returns can be referenced.
- `evaluationInterval: 1m` runs the query once a minute, the minimum. See the [AlertRule spec](/docs/reference/alert-spec) for every field and constraint.
- Link a runbook to the rule with `spec.runbook` so responders get a documented procedure when it fires.

## Test the change

Stage it into a preview. The rule deploys under a preview name, evaluates for real, but never sends notifications:

```sh
everr apply ./everr --preview
```

Expected output ends with a shareable link:

```
Destination org: «Acme Corp»
AlertRule: 1 created, 0 updated, 0 deleted
  + eventloop-delay
Preview: https://app.everr.dev/dashboards?preview=my-branch
```

Open the link, go to **Alerts**, and watch the rule's firing/ok state before publishing. Previews expire on their own 7 days after their last apply.

## Publish it

```sh
everr apply ./everr
```

Apply first prints a plan, then asks you to confirm before writing. Answer the `Apply to «Acme Corp»?` prompt, or pass `--yes` (`-y`) to skip it (required in CI and piped contexts). Expected output, after confirming:

```
Destination org: «Acme Corp»
AlertRule: 1 created, 0 updated, 0 deleted
  + eventloop-delay
```

If there are no changes, apply prints `Nothing to apply.` and exits without prompting: re-running is idempotent.

## Open it in Everr

Open Everr and go to **Alerts** (`/alerts`). Your `eventloop-delay` rule appears in the **Rules** list with its current state. Open it:

- The facts under the title say how the rule behaves: its severity, how often it evaluates, how long a breach has to last before it fires, how many non-breaching evaluations resolve it, and where it delivers.
- **Breaching instances** counts the instances over the threshold right now. The **Signal history** chart below plots the rule's own signal against its threshold, so a breach that comes and goes is visible.
- If the query errors, the rule shows an evaluation error on the detail page. Fix the SQL and re-apply.

## Get notified

Seeing the alert fire in the UI needs no setup. To actually receive it, create a channel on the Notifications page: Slack, Discord, Telegram, or any HTTPS webhook. Your first channel becomes the organization's default destination, so one channel is a complete setup. See [Set up alert notifications](/docs/guides/set-up-notifications).

## Change and re-apply

Edit the file (say, tighten `condition.threshold` to `200`) and apply again. A changed rule is updated in place; the slug and URL don't change because the slug didn't. Reconciliation is delete-by-default within the repoid: delete the file and apply, and Everr removes the rule.

```sh
rm everr/eventloop-delay.alert.yaml
everr apply ./everr
```
