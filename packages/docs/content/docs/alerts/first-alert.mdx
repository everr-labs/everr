This is the shortest path to a working alert: write one rule, reconcile it with `everr apply`, and open it in the Alerts UI. By the end you'll have a real alert and the workflow you'll reuse for every alert after.

## Before you start

- The CLI is installed. See [Install](/docs/getting-started/install).
- You have telemetry in Everr to query. If not, start with [Your first trace](/docs/getting-started/first-trace). This tutorial alerts on Node.js runtime metrics.
- **`everr apply` uses your `everr cloud login` session by default** and prints the destination organization before writing. For CI or non-interactive use, set `EVERR_API_TOKEN` to an organization ingest key:

  ```sh
  export EVERR_API_TOKEN="<your-org-ingest-key>"
  ```

  See the [`everr apply` reference](/docs/reference/cli#dashboards-gitops).

## Let your assistant write it

The fastest way to a good alert is to ask your coding assistant. Everr ships the `everr-setup-telemetry` skill, which teaches the assistant the `AlertRule` format and how to ground a rule in your real telemetry. Run it from the repository that emits the telemetry, so it can connect services, routes, and metrics back to the code that produces them.

A concrete prompt:

```text
Use the everr-setup-telemetry skill to create an Everr alert for this repo.
```

The assistant inspects your data, picks the signal, writes the rule, and validates it against `everr cloud query` and a dry-run — so the threshold is grounded in your actual baselines rather than guessed. The rest of this page walks through the same steps by hand so you understand what it produces.

## Create the apply directory

Make a directory to hold your alerts and add an `everr.yaml` manifest at its root. Apply discovers and reconciles everything under this directory.

```sh
mkdir -p alerts
```

The manifest declares one stable `repoid`, a UUID you pick once and keep. It scopes what apply manages (its prune boundary).

`alerts/everr.yaml`:

```yaml
repoid: "2f8e3f90-9d1c-5d5f-a0f9-2d8e7f4a25d1"
```

Generate your own UUID (for example with `uuidgen`) and keep it stable, changing it makes apply treat the rules as a different repo, so it would delete the old ones and recreate them. The manifest accepts only `repoid`; any other key is rejected. See the [manifest reference](/docs/alerts/alert-spec#manifest).

## Write the rule

`alerts/eventloop-delay.yaml`:

```yaml
kind: AlertRule
metadata:
  name: eventloop-delay
spec:
  display:
    name: Node.js event loop delay
    description: Services whose event loop is blocked over the last 5 minutes.
  evaluationInterval: 1m
  notificationMessage:
    title: "${ServiceName} event loop is lagging"
    description: "p99 event loop delay averaged ${p99_delay_ms}ms over the last 5 minutes"
  query: |
    SELECT
      ServiceName,
      round(avg(Value) * 1000, 1) AS p99_delay_ms
    FROM metrics_gauge
    WHERE MetricName = 'nodejs.eventloop.delay.p99'
      AND TimeUnix >= now() - INTERVAL 5 MINUTE
    GROUP BY ServiceName
    HAVING p99_delay_ms > 100
    ORDER BY p99_delay_ms DESC
```

A few things worth noting:

- `metadata.name` is the rule's **slug** and identity. Use lowercase letters, digits, and hyphens.
- The query **is** the condition: one row per service over the threshold → each such service is a firing instance; nothing over the threshold → no rows → resolved. `nodejs.eventloop.delay.p99` is a Node.js runtime metric reported in seconds, so the query converts it to milliseconds. A healthy service sits around 10ms, so `HAVING p99_delay_ms > 100` stays quiet until the event loop is genuinely blocked, tune that number to your services. Averaging over the 5-minute window keeps a single momentary blip from paging.
- `ServiceName` is a string column, so Everr uses it as each instance's identity automatically, one alert instance per service. See [Writing alert queries](/docs/alerts/writing-queries).
- `notificationMessage` is templated with `${ServiceName}` and `${p99_delay_ms}` from that instance's row; only columns the query returns can be referenced.
- `evaluationInterval: 1m` runs the query once a minute (the minimum).

## Test the change

To validate that the queries are correct and the file is valid use dry-run

```sh
everr apply ./alerts --dry-run
```

```
(dry run) AlertRule: 1 created, 0 updated, 0 deleted
  + eventloop-delay
```

## Publish it

```sh
everr apply ./alerts
```

Apply first prints a plan, then, asks you to confirm before writing. 
Answer the `Apply to «Acme Corp»?` prompt, or pass `--yes` (`-y`) to skip it (required in CI and piped contexts).

```
(plan) Destination org: «Acme Corp»
(plan) AlertRule: 1 created, 0 updated, 0 deleted
  + eventloop-delay
```

After you confirm, it runs the apply and prints the same summary without the `(plan)` prefix:

```
Destination org: «Acme Corp»
AlertRule: 1 created, 0 updated, 0 deleted
  + eventloop-delay
```

If there are no changes, apply prints `Nothing to apply.` and exits without prompting. Re-running is idempotent, apply again and you'll see `Nothing to apply.`

## Open it in Everr

Open Everr and go to **Alerts** (`/alerts`). Your `eventloop-delay` rule appears in the **Rules** list with its current state. Open it:

- The **Configuration** card shows the evaluation interval, instance labels, and the **Last evaluated** time.
- When a service crosses the threshold, the **Firing instances** card lists one row per firing service with a **Firing since** time. If nothing is firing, it shows the resolved state.
- If the query errors, the rule shows an evaluation error on the detail page, fix the SQL and re-apply.

## Get notified

Seeing the alert fire in the UI needs no setup. To actually receive it via Telegram, configure a channel. See [Notifications](/docs/alerts/notifications).

## Change and re-apply

Edit the file, say, tighten the threshold to `HAVING p99_delay_ms > 200`, and apply again. A changed rule is updated in place; the slug and URL don't change because the slug didn't.

To remove a rule, delete its file and apply, reconciliation is delete-by-default within the repoid:

```sh
rm alerts/eventloop-delay.yaml
everr apply ./alerts
```

```
(plan) Destination org: «Acme Corp»
(plan) AlertRule: 0 created, 0 updated, 1 deleted
  - eventloop-delay
```
