title: Notifications
description: Route firing and resolved alerts to receivers with matchers, and control grouping, repeats, silences, and inhibitions.

Alert rules are defined as code, but delivery is configured in the app and applies across the whole organization. Everything below lives under **Alerts** in Everr: routing on the **Routing** tab, silences under **Monitor**.

## The delivery pipeline

When an alert fires or resolves, it walks a fixed path:

1. **Routes** are checked top to bottom by priority; the first route whose matchers fit the alert's labels decides the receiver.
2. The matched **receiver** delivers the notification (Slack, email, webhook, PagerDuty, or Telegram).
3. Alerts that match **no route** fall through to the **firehose**: every subscribed webhook receives them.

Silences and inhibitions suppress delivery without stopping evaluation.

## Receivers

A receiver is a named delivery target. Create and delete receivers on the Routing tab; routes reference them by name.

Channel types: **email** (recipient addresses), **Slack** (an [Incoming Webhook](https://api.slack.com/messaging/webhooks) URL), **webhook** (any HTTPS endpoint), **PagerDuty** (an integration key), and **Telegram** (a bot token and chat ID, see Telegram's [BotFather guide](https://core.telegram.org/bots/features#botfather)).

Secret fields (webhook URLs, tokens, keys) are write-only: after saving, Everr shows them redacted. To change one, create the receiver again under the same name with the new value.

## Routes

A route is a set of **matchers** (label comparisons such as `severity = critical`, with equals, not-equals, and regex operators), a target receiver, and a priority. Routes are checked in priority order and the first match wins.

Each route also controls timing:

- **Group by** collects instances that share the chosen labels into one notification.
- **Group wait** is how long to hold a new group before the first send, letting related instances batch together.
- **Group interval** is the minimum time between updates for an already-notified group.
- **Repeat interval** re-sends the notification while the alert stays firing, so a long-lived incident is not silent after the first message.

## Inhibitions

An inhibition suppresses downstream alerts while a related, higher-level alert is already firing: while alerts matching the **source** matchers fire, alerts matching the **target** matchers are suppressed. Optional **equal labels** scope it to pairs that share the same value for those labels, so a database outage in `region=eu` only inhibits alerts from the same region.

## Firehose

The firehose is the fallback and the integration point: every alert that matches no route is delivered to every webhook URL subscribed here. Point it at an internal service to build custom fan-out without defining routes.

## Silences

To stop notifications for a known issue or maintenance window without touching the rule, create a **silence** under **Monitor**: matchers select the alerts, a time window bounds the suppression, and a comment records why. Silences can be scheduled ahead of a maintenance window. The rule keeps evaluating the whole time; silenced alerts are suppressed from delivery and recorded in the event stream.
