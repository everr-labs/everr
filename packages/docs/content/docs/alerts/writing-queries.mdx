---
title: Writing Alert Queries
description: Express thresholds, alert per instance, and choose an evaluation interval in an AlertRule query.
---

An alert's `spec.query` is plain ClickHouse SQL, and the rule is simple: every row the query returns is a firing instance, and an empty result means resolved. Everything else on this page follows from that one fact. Unlike panel queries, alert SQL does **not** support `${...}` template tokens — those are only for message templates.

## Express a threshold

There is no separate threshold field. You put the condition in the query itself, so it returns rows only when something is actually wrong. Use `WHERE` to scope the data you look at, and `HAVING` to threshold an aggregate:

```sql
SELECT ServiceName, count() AS errors
FROM logs
WHERE Timestamp >= now() - INTERVAL 15 MINUTE
  AND SeverityNumber >= 17
GROUP BY ServiceName
HAVING errors > 10        -- fire only above the threshold
```

When no service crosses the threshold the query returns nothing, and the alert is resolved.

## Instance identity

By default, an instance's identity is the set of **string** columns the query returns. The query above returns `ServiceName` (a string) and `errors` (a number), so it produces one instance per service automatically — a single rule scales across every service instead of needing one rule each. Because the numeric `errors` column is not part of identity, a service stays the same instance as its error count rises and falls.

Override the default with `spec.instanceLabels` when it isn't right for you — for example when the query returns extra string columns you don't want in the identity, or when you want a specific subset. The identity then becomes exactly the listed columns:

```yaml
spec:
  instanceLabels: [ServiceName]   # identity is exactly this column
  query: |
    SELECT ServiceName, Environment, count() AS errors
    FROM logs
    WHERE Timestamp >= now() - INTERVAL 15 MINUTE AND SeverityNumber >= 17
    GROUP BY ServiceName, Environment
    HAVING errors > 10
```

Match `instanceLabels` to the columns you `GROUP BY`, and make sure each instance is a single row — if two rows share the same identity in one result, they collapse into one instance.

## Choose an evaluation interval

`spec.evaluationInterval` is an `<integer><s|m|h|d>` duration with a minimum of `1m` (for example `1m`, `5m`, `1h`). Align the query's time window to the interval: a 15-minute lookback evaluated every minute smooths transient spikes, because a single one-off error keeps the rule firing for the length of the window.

Everr notifies on the firing and resolved edges as soon as the rule evaluates. There is no separate "for" or pending duration to wait out, so use the query window itself to control flapping.

## Keep results small

The firing set *is* the rows the query returns, so return only what's firing — push the filtering and the threshold into the SQL with `WHERE` and `HAVING`. Emit one row per instance, avoid `SELECT *` on large sets, and add a `LIMIT` for safety on broad queries.
