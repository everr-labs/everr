---
title: Organizing Dashboards and Sources
description: Use directories for folders, manage dashboards from multiple repos with sources, and apply from CI.
---

As you add dashboards, two things matter: how they're grouped in the UI, and how multiple teams or repos contribute without stepping on each other. Both come from how `everr apply` works.

## Folders come from directories

The dashboards index shows a folder tree. You don't define folders — they're derived from the directory each file sits in, relative to the directory you applied.

```
dashboards/
  overview.yaml                 -> root
  platform/
    api-latency.yaml            -> folder "platform"
    db_health.yaml              -> folder "platform"
  team_payments/
    checkout/
      funnel.yaml               -> folder "team payments / checkout"
```

Directory segments become the folder path, joined by ` / `. Underscores and hyphens in segment names are shown as spaces (`team_payments` → `team payments`). Move a file to a different directory and re-apply, and the dashboard moves folders. There are no folder objects to create, rename, or delete.

## Sources: who owns what

Every apply runs under a `--source`. A source is an identifier you choose for a set of dashboards — typically one per repo or team (`platform`, `team-payments`). It does two things:

1. **Namespaces identity.** A dashboard's full identity is `source` + `slug`, and its URL is `/dashboards/<source>/<slug>`. Two sources can both have an `overview` dashboard without colliding.
2. **Scopes reconciliation.** `everr apply --source=X` makes source `X`'s dashboards exactly match the applied tree — and only `X`'s. It can never read, modify, or delete another source's (or another organization's) dashboards.

This is what makes multiple repos safe. Each repo applies its own source from its own CI; a repo can only ever change its own dashboards.

```sh
# in the platform repo
everr apply ./dashboards --source=platform

# in the payments repo, independently
everr apply ./dashboards --source=team-payments
```

## Delete-by-default, scoped to the source

`everr apply` is declarative. For the applied source it will:

- **create** dashboards whose files are new,
- **update** dashboards whose files changed,
- **delete** dashboards whose files are no longer present.

There is no separate prune step — removing a file removes the dashboard on the next apply. It's safe because deletion only ever applies within the source you're applying. Always preview with `--dry-run` first:

```sh
everr apply ./dashboards --source=platform --dry-run
```

```
(dry run) Dashboard: 1 created, 2 updated, 1 deleted
  + db-health
  ~ api-latency
  ~ overview
  - legacy-dashboard
```

## Applying from CI

`everr apply` is token-only: it always authenticates with an organization **ingest key**, never an interactive session — so the same command works identically on a laptop and in CI. Set the key in `EVERR_API_TOKEN` and the API base URL in `EVERR_API_URL` (or rely on the one persisted by a prior `everr cloud login`).

```yaml
# .github/workflows/dashboards.yml
name: Apply dashboards
on:
  push:
    branches: [main]
    paths: ["dashboards/**"]
jobs:
  apply:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: everr apply ./dashboards --source=platform
        env:
          EVERR_API_TOKEN: ${{ secrets.EVERR_API_TOKEN }}
          EVERR_API_URL: ${{ vars.EVERR_API_URL }}
```

Gate the apply on your default branch so dashboards change only after review — the whole point of defining them as code. To preview in a pull request, run the same command with `--dry-run` and surface the diff.

See the [`everr apply` CLI reference](/docs/reference/cli#dashboards-gitops) for the full flag and environment list.
