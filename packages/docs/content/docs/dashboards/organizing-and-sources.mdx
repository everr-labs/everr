---
title: Organizing Dashboards and Projects
description: Use directories for folders, a repoid to manage dashboards from multiple repos, and apply from CI.
---

As you add dashboards, two things matter: how they're grouped in the UI, and how multiple teams or repos contribute without stepping on each other. Both come from how `everr apply` works.

## Folders come from directories

Your declarations live in an `everr/` directory at your repo root, flat and named by kind (`*.dashboard.yaml`). The dashboards index shows a folder tree: you don't define folders — they're derived from the directory each file sits in, relative to the directory you applied. Subdirectories are optional; use them when you want folders.

```
everr/
  everr.yaml                          -> optional explicit repoid override
  overview.dashboard.yaml             -> root
  platform/
    api-latency.dashboard.yaml        -> folder "platform"
    db_health.dashboard.yaml          -> folder "platform"
  team_payments/
    checkout/
      funnel.dashboard.yaml           -> folder "team payments / checkout"
```

Directory segments become the folder path, joined by ` / `. Underscores and hyphens in segment names are shown as spaces (`team_payments` → `team payments`). Move a file to a different directory and re-apply, and the dashboard moves folders. There are no folder objects to create, rename, or delete.

## The repo identity scopes what you manage

The `repoid` is inferred automatically from the repository's `origin` git remote, normalized to the slug `host/owner/repo`. Equivalent ssh, https, and scp clone URLs collapse to the same identity, so one repo means one boundary. No manifest file is needed.

An optional `everr.yaml` (or `everr.yml`) at the apply root can override the inferred identity. It accepts exactly one key:

```yaml
# everr/everr.yaml
repoid: "my-explicit-id"
```

The `repoid` is the **apply ownership boundary**. `everr apply` reconciles exactly the resources previously applied under this id — nothing else is touched. Use it as an escape hatch for local-only repositories, non-git directories, or when you need to pin an explicit name. Never reuse a repoid across unrelated repos, and never change it for an existing setup (that orphans everything applied under the old id, leaving the old resources live but unmanaged). It is the only key the manifest accepts.

## Projects namespace identity

Independently of the repoid, every dashboard may declare a `metadata.project` (defaults to `default`). A project is an identifier you choose for a set of dashboards — typically one per team (`platform`, `team-payments`). It **namespaces identity**: a dashboard's full identity is `project` + `slug`, and its URL is `/dashboards/<project>/<slug>`, so two projects can both have an `overview` dashboard without colliding. It is optional and does **not** need to appear in the manifest.

## Multiple repos stay isolated by identity

Each repo's identity is its own remote slug, so applies never collide: `everr apply` only ever touches resources under that repo's identity. It can never modify another repo's (or another organization's) dashboards. No manifest is needed to keep them separate.

```yaml
# platform repo — everr/api-latency.dashboard.yaml
kind: Dashboard
metadata:
  name: api-latency
  project: platform
spec:
  ...
```

```yaml
# payments repo — everr/checkout-funnel.dashboard.yaml
kind: Dashboard
metadata:
  name: checkout-funnel
  project: team-payments
spec:
  ...
```

If you need to pin an explicit identity, use the optional `everr.yaml` override described above.

Apply each repo independently:

```sh
# in the platform repo
everr apply ./everr

# in the payments repo, independently
everr apply ./everr
```

## Full reconcile, scoped to the repoid

`everr apply` is declarative. For everything under the repoid it makes the live dashboards exactly match the files:

- **create** dashboards whose files are new,
- **update** dashboards whose files changed,
- **delete** dashboards whose files are no longer present.

There is no separate prune step — removing a file removes the dashboard on the next apply, moving a dashboard's file within the tree relocates it (no duplicate), and emptying the tree removes its last dashboard. It's safe because reconciliation only ever applies within the repo's identity. Always preview with `--dry-run` first:

```sh
everr apply ./everr --dry-run
```

```
(dry run) Dashboard: 1 created, 2 updated, 1 deleted
  + db-health
  ~ api-latency
  ~ overview
  - legacy-dashboard
```

## Applying from CI

By default `everr apply` uses your `everr cloud login` session and prints the destination organization before writing. CI runners do not include the Everr CLI by default, so install it with `everr-action` before calling `everr apply`. For CI and other non-interactive contexts, set `EVERR_API_KEY` to an organization API key with the `apply` scope (the same `ek_` keys you mint for ingest; the Capabilities column shows what each key can do). The legacy `EVERR_API_TOKEN` is still accepted. If `EVERR_API_URL` is not set, the base URL falls back to the one saved by a prior `everr cloud login`.

```yaml
# .github/workflows/dashboards.yml
name: Apply dashboards
on:
  push:
    branches: [main]
    paths: ["everr/**"]
jobs:
  apply:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: everr-labs/everr-action@v0
        with:
          install-cli: "true"
          resource-usage: "false"

      - run: everr apply ./everr --yes
        env:
          EVERR_API_KEY: ${{ secrets.EVERR_API_KEY }}
          EVERR_API_URL: ${{ vars.EVERR_API_URL }}
```

`--yes` (or `-y`) skips the confirmation prompt that apply shows before writing. It is required in non-interactive contexts such as CI or piped scripts. Use `--dry-run` instead to preview the diff without writing anything.

Gate the apply on your default branch so dashboards change only after review — the whole point of defining them as code. To preview in a pull request, run the same command with `--dry-run` and surface the diff.

See the [`everr apply` CLI reference](/docs/reference/cli#dashboards-gitops) for the full flag and environment list.
