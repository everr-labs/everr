title: Dashboards
description: Custom dashboards defined as code, reconciled into Everr with the CLI, and rendered read-only from your ClickHouse data.
---

Everr dashboards are **defined as code**. You write dashboards as YAML or JSON files in a Git repository, then reconcile them into Everr with `everr apply`. The Everr app **renders** them — it runs their queries and draws the charts — but it never edits them. Git is the source of truth.

This is a deliberate, gitops-style model. There is no click-to-edit grid, no save button, no in-app authoring. A dashboard changes when a file changes and you apply it — so dashboards are reviewable in pull requests, versioned with your code, and reproducible across environments.

## The model

A dashboard file follows the [Perses](https://perses.dev) data model — `kind`, `metadata`, and `spec` — with `panels`, `layouts`, and `variables`. Panels run ClickHouse SQL against your telemetry and render it with a visualization (time series, table, or stat). See the [Dashboard spec reference](/docs/dashboards/dashboard-spec) for the full shape.

```yaml
kind: Dashboard
metadata:
  name: api-latency        # the slug; URL becomes /dashboards/<project>/api-latency
  project: platform        # optional; defaults to "default"
spec:
  display:
    name: API Latency
  panels:
    p99:
      kind: Panel
      spec:
        display: { name: p99 latency }
        plugin: { kind: TimeSeriesChart, spec: { unit: ms } }
        queries:
          - kind: ClickHouseSQL
            spec:
              plugin:
                kind: ClickHouseSQL
                spec:
                  query: |
                    SELECT toStartOfInterval(Timestamp, INTERVAL {step:UInt32} SECOND) AS ts,
                           quantile(0.99)(Duration) / 1e6 AS p99_ms
                    FROM traces
                    WHERE Timestamp >= {from:String} AND Timestamp <= {to:String}
                    GROUP BY ts ORDER BY ts
  layouts:
    - kind: Grid
      spec:
        items:
          - { x: 0, y: 0, width: 24, height: 8, content: { $ref: "#/spec/panels/p99" } }
```

## Key concepts

- **Project.** Every dashboard may set a `metadata.project` (defaults to `default`). A project is an identifier you choose for a set of dashboards — typically one per team (`platform`, `team-payments`). It namespaces identity and URL; it is optional and does not appear in the manifest.
- **Identity is `project` + `slug`.** A dashboard's slug comes from `metadata.name` — set it explicitly. Its URL is `/dashboards/<project>/<slug>`. Two different projects can use the same slug without colliding.
- **Declarations live in `everr/`.** Put your files in an `everr/` directory at your repo root, flat and named by kind — dashboards are `*.dashboard.yaml` (alerts `*.alert.yaml`, runbooks `*.runbook.yaml`). The suffix is a naming convention; apply routes by the `kind:` field.
- **Folders come from directories.** The (optional) subdirectory a file lives in becomes its folder path in the dashboards tree. There are no folder objects to create or own — move a file, move the dashboard. See [Organizing dashboards](/docs/dashboards/organizing-and-sources).
- **The repo identity scopes the apply.** The `repoid` is inferred from the repository's `origin` remote (normalized to `host/owner/repo`). No manifest file is needed; an optional `everr.yaml` (or `everr.yml`) at the root can pin an explicit `repoid` override. See [Organizing dashboards](/docs/dashboards/organizing-and-sources).
- **Apply is declarative (delete-by-default).** `everr apply` makes the dashboards under the repoid exactly match its directory tree. A file you add is created, a changed file is updated, and a file you remove is **deleted**. Reconciliation is scoped to the repo's identity — no other repo's dashboards are affected. Use `--dry-run` to preview the diff first.
- **Apply auth and confirmation.** By default `everr apply` uses your `everr cloud login` session and prints the destination organization before writing. It asks for confirmation before applying changes (creates, updates, and deletes all prompt); pass `--yes` (or `-y`) to skip the prompt (required in CI and piped contexts). If there are no changes it prints `Nothing to apply.` and exits without prompting. For CI, install the CLI with `everr-action` before calling `everr apply`, then set `EVERR_API_KEY` to an organization API key with the `apply` scope instead of relying on an interactive session. The legacy `EVERR_API_TOKEN` is also accepted.
