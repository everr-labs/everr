This is the shortest path to a working dashboard: write one YAML file, reconcile it with `everr apply`, and open it in Everr. By the end you'll have a real dashboard rendered from your ClickHouse data and the workflow you'll use for every dashboard after.

## Before you start

- The CLI is installed. See [Install](/docs/getting-started/install).
- You have telemetry in Everr to query. If not, start with [Your first trace](/docs/getting-started/first-trace).
- **`everr apply` uses your `everr cloud login` session by default** and prints the destination organization before writing. For CI or non-interactive use, set `EVERR_API_TOKEN` to an organization ingest key:

  ```sh
  export EVERR_API_TOKEN="<your-org-ingest-key>"
  ```

  See the [`everr apply` reference](/docs/reference/cli#dashboards-gitops).

## Let your assistant write it

The fastest way to a useful dashboard is to ask your coding assistant. Everr ships the `everr-write-dashboards` skill, which teaches the assistant the dashboard file format and how to build panels from your real telemetry. Run it from the repository that emits the telemetry, so it can connect services, routes, and metrics back to the code that produces them.

A concrete prompt:

```text
Use the everr-write-dashboards skill to create an Everr dashboard for this repo.
```

The assistant inspects your data, picks the panels and queries, writes the file, and validates it against `everr cloud query` and a dry-run — so the charts render real data rather than guessed column names. The rest of this page walks through the same steps by hand so you understand what it produces.

## Create a dashboard file

Make a directory to hold your dashboards and add one file. The directory is the unit you'll apply.

```sh
mkdir -p dashboards
```

Every apply directory needs an `everr.yaml` (or `everr.yml`) at its root declaring a stable `repoid`. The repoid is the apply ownership boundary — apply reconciles exactly the resources previously applied under it.

`dashboards/everr.yaml`:

```yaml
repoid: "2f8e3f90-9d1c-5d5f-a0f9-2d8e7f4a25d1"
```

Use one stable id per repository (a UUID is a good default); never change it for an existing setup. Dashboards may set an optional `metadata.project` to namespace their identity and URL, but it does not appear in the manifest.

`dashboards/api-latency.yaml`:

```yaml
kind: Dashboard
metadata:
  name: api-latency
  project: demo            # optional; defaults to "default"
spec:
  display:
    name: API Latency
  panels:
    p99:
      kind: Panel
      spec:
        display: { name: p99 latency (ms) }
        plugin:
          kind: TimeSeriesChart
          spec: { unit: ms, showLegend: true }
        queries:
          - kind: ClickHouseSQL
            spec:
              plugin:
                kind: ClickHouseSQL
                spec:
                  query: |
                    SELECT toStartOfInterval(Timestamp, INTERVAL {step:UInt32} SECOND) AS ts,
                           quantile(0.99)(Duration) / 1e6 AS p99
                    FROM traces
                    WHERE Timestamp >= {from:String} AND Timestamp <= {to:String}
                    GROUP BY ts
                    ORDER BY ts
  layouts:
    - kind: Grid
      spec:
        items:
          - x: 0
            y: 0
            width: 24
            height: 8
            content: { $ref: "#/spec/panels/p99" }
```

A few things worth noting:

- `metadata.name` is the **slug** — the dashboard's stable identity and its URL. Use lowercase letters, digits, and hyphens.
- `metadata.project` groups dashboards into a named set. It defaults to `default` when omitted. A dashboard's URL is `/dashboards/<project>/<slug>`, so two projects can share the same slug without colliding.
- The panel's query must alias its time column to a recognized name (`ts`, `time`, or `timestamp`). The time-series chart uses that column for the x-axis and treats the remaining numeric columns as series. See [Panels and visualizations](/docs/dashboards/panels-and-visualizations).
- The `{from:String}` / `{to:String}` parameters carry the dashboard's selected time range. They aren't injected automatically, so include the `WHERE Timestamp >= {from:String} AND Timestamp <= {to:String}` filter — otherwise the query scans all history and ignores the picker.
- `{step:UInt32}` is an adaptive bucket width in seconds — Everr sizes it so the chart renders ~500 points at any range. See [Adaptive bucketing](/docs/dashboards/panels-and-visualizations#adaptive-bucketing).
- The `layouts` grid places the panel. `content.$ref` points at the panel key under `spec.panels` (here, `p99`). The grid is 24 columns wide.

## Preview the change

Always dry-run first. It computes the diff and writes nothing:

```sh
everr apply ./dashboards --dry-run
```

```
(dry run) Dashboard: 1 created, 0 updated, 0 deleted
  + api-latency
```

The project each dashboard belongs to comes from `metadata.project` in the file. Pick a meaningful name for your repo or team; it defaults to `default` when omitted.

## Apply it

```sh
everr apply ./dashboards
```

Apply first prints a plan, then — because there are changes — asks you to confirm before writing. Answer the `Apply to «Acme Corp»?` prompt, or pass `--yes` (`-y`) to skip it (required in CI and piped contexts).

```
(plan) Destination org: «Acme Corp»
(plan) Dashboard: 1 created, 0 updated, 0 deleted
  + api-latency
```

After you confirm, it runs the apply and prints the same summary without the `(plan)` prefix:

```
Destination org: «Acme Corp»
Dashboard: 1 created, 0 updated, 0 deleted
  + api-latency
```

If there are no changes, apply prints `Nothing to apply.` and exits without prompting.

Re-running is idempotent — apply again and you'll see `Nothing to apply.`

## View it

Open Everr and go to **Dashboards**, or navigate directly to:

```
/dashboards/demo/api-latency
```

(Replace `demo` with the `metadata.project` value you used, or `default` if you omitted it.)

The panel renders live, driven by the global time-range picker. Adjust the time range and the query re-runs; drag across a time-series panel to zoom.

## Change and re-apply

Edit the file — say, add a second panel or change the query — and apply again. A changed dashboard is updated in place; the URL never changes because the slug didn't.

```sh
everr apply ./dashboards
```

```
(plan) Destination org: «Acme Corp»
(plan) Dashboard: 0 created, 1 updated, 0 deleted
  ~ api-latency
```

After confirming (or with `--yes`):

```
Destination org: «Acme Corp»
Dashboard: 0 created, 1 updated, 0 deleted
  ~ api-latency
```

And to remove a dashboard, delete its file and apply — reconciliation is delete-by-default within the project:

```sh
rm dashboards/api-latency.yaml
everr apply ./dashboards
```

```
(plan) Destination org: «Acme Corp»
(plan) Dashboard: 0 created, 0 updated, 1 deleted
  - api-latency
```

After confirming:

```
Destination org: «Acme Corp»
Dashboard: 0 created, 0 updated, 1 deleted
  - api-latency
```
