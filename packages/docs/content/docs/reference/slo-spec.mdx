An `SLO` is a resource with three top-level keys. Everr validates it on `everr apply` and again on read. The `spec` holds a ClickHouse query that counts good and valid events over a window, a reliability target, and the burn-rate tiers that decide when to alert. For the model behind these fields see [how SLOs work](/docs/concepts/how-slos-work).

```yaml
kind: SLO
metadata:
  name: <slug>
spec:
  { ... }
```

| Key | Type | Notes |
| --- | --- | --- |
| `kind` | `"SLO"` | Selects the reconciler. Required. |
| `metadata.name` | string | The SLO's **slug** and identity. Required. 1 to 128 chars of `[A-Za-z0-9_.-]`, tenant-unique. |
| `metadata.project` | string | Optional project the SLO belongs to. Defaults to `default`. |
| `metadata.labels` | map (string to string) | Optional free-form labels carried on the resource. |
| `spec` | object | The SLO contents, below. |

## `spec`

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `sli.sql` | string | yes | ClickHouse SQL returning `good` and `valid` counts for the window. Must reference `{window_start:DateTime}` and `{window_end:DateTime}`. See [the SLI contract](#the-sli-query) below. |
| `sli.labelColumns` | [string] | no | Columns that fan the SLO out into per-group SLIs, one budget per distinct value. Omit for a scalar SLO. ≥1 entry when present, and the SQL must actually project and `GROUP BY` them. See [grouping](#grouping). |
| `targetPercent` | number | yes | The objective, strictly `> 0` and `< 100`. `99.9` means 99.9% of valid events must be good. |
| `timeWindow` | string | yes | The rolling budget window: `<int><m\|h\|d\|w>`, for example `30d`. No seconds unit, and at most 366 days. The object form `{ duration, isRolling: true }` is also accepted; calendar-aligned windows (`isRolling: false`) are rejected. |
| `minValidEvents` | int | no | Low-traffic floor: a tier's long window is only allowed to fire once it has seen at least this many valid events, suppressing noise from thin data. Omit to disable. |
| `tiers` | [object] | no | Burn-rate tiers. Omit to evaluate the [canonical three](#burn-rate-tiers). When present, ≥1 entry, and they replace the canonical set entirely. |
| `annotations` | map (string to string) | no | Free-form key/value pairs passed through to the engine alongside Everr's generated annotations. Keys starting with `everr.` are reserved and rejected. |

An SLO created directly through the engine API that carries `everr.name` and a matching `everr.repoid` is treated as owned by that repo's config: the next `everr apply` adopts it, and prunes it if no YAML file declares it.

## The SLI query

`sli.sql` is a single read-only `SELECT`. The engine runs it once per window per group and reads two numeric columns from the result:

- `good`: the count of events that met the objective.
- `valid`: the count of events eligible to be judged (the denominator).

Both are required, by those exact names. The achieved reliability for the window is `good / valid`, and the error budget is what remains of the `1 - targetPercent/100` allowance.

The window is supplied as two ClickHouse query parameters, and the SQL **must** reference both:

- `{window_start:DateTime}`: inclusive lower bound of the rolling window.
- `{window_end:DateTime}`: exclusive upper bound (now).

```sql
SELECT countIf(status < 500) AS good, count() AS valid
FROM checkouts
WHERE ts >= {window_start:DateTime} AND ts < {window_end:DateTime}
```

Only these two parameters are available. The SQL does not support `${...}` templating. Its validity against your schema is checked by the engine's dry-run test during apply.

## Grouping

A scalar SLO returns one `good`/`valid` row and tracks one budget. Adding `sli.labelColumns` turns one definition into one SLI per distinct combination of those columns, each with an independent budget and independent burn-rate tiers.

```yaml
spec:
  sli:
    sql: >-
      SELECT ServiceName, countIf(status < 500) AS good, count() AS valid
      FROM requests
      WHERE ts >= {window_start:DateTime} AND ts < {window_end:DateTime}
      GROUP BY ServiceName
    labelColumns: [ServiceName]
```

The grouping is driven by the SQL, not by `labelColumns` alone. If the query does not `SELECT` and `GROUP BY` the listed columns, every event collapses into one group and the fan-out does nothing, even though `labelColumns` is set. Keep the two in sync.

Two label names are reserved because the SLO pipeline injects them: `slo` (the synthetic routing label) and `slo_tier` (the per-tier instance discriminator). Column aliases starting with `__cc_` are reserved for the engine. A `labelColumns` entry using any of these is rejected at apply time.

## Burn-rate tiers

Each tier fires when the burn rate exceeds `burnRate` over **both** its long and short windows at once. Omit `spec.tiers` and the engine evaluates its canonical three, calibrated for a 30-day window:

| Tier | Burn rate | Long window | Short window | Severity |
| --- | --- | --- | --- | --- |
| `fast-burn` | 14.4× | 1h | 5m | critical |
| `slow-burn` | 6.0× | 6h | 30m | critical |
| `ticket` | 1.0× | 3d | 6h | warning |

To override them, define your own tiers. Setting `tiers` replaces the canonical set entirely (it is not merged), so list every tier you want.

```yaml
spec:
  tiers:
    - name: page
      burnRate: 14.4
      longWindow: 1h
      shortWindow: 5m
      severity: critical
    - name: ticket
      burnRate: 1
      longWindow: 3d
      shortWindow: 6h
      severity: warning
```

| Tier field | Type | Notes |
| --- | --- | --- |
| `name` | string | Non-empty. Names the tier in the UI and rides on its instances as `slo_tier`. |
| `burnRate` | number | The multiple that fires the tier. Must be `> 0`. |
| `longWindow` | string | The sustained window (`<int><m\|h\|d\|w>`). Must be greater than `shortWindow`. |
| `shortWindow` | string | The recency window. |
| `severity` | `info` \| `warning` \| `critical` | The severity the tier's instances fire at. |

## Manifest

The apply identity (the `repoid`) is inferred from the repository's `origin` git remote, or set explicitly in an `everr.yaml` at the apply root. This is the same manifest that governs alert rules and dashboards; see the [AlertRule spec](/docs/reference/alert-spec#manifest) for the full rules.

SLO declarations sit flat in `everr/`, named `*.slo.yaml`. `everr apply ./everr` discovers every `kind: SLO` document under the directory and makes the live SLOs for that repoid exactly match the tree: new documents are created, changed ones updated, and removed ones **deleted**. The kind suffix is a naming convention only: apply routes by the `kind:` field. Use `--preview` to stage changes without notifying (preview SLOs evaluate fully but the dispatcher never sends). See the [`everr apply` reference](/docs/reference/cli#dashboards-gitops).

## Constraints and errors

- `metadata.name` must be 1 to 128 chars of `[A-Za-z0-9_.-]`.
- `sli.sql` must be non-empty and reference both `{window_start:DateTime}` and `{window_end:DateTime}`.
- `targetPercent` must be strictly `> 0` and `< 100`.
- `timeWindow` must be `<int><m|h|d|w>`, at most 366 days; calendar windows (`isRolling: false`) are rejected.
- `minValidEvents`, when set, must be a non-negative integer.
- `sli.labelColumns` needs ≥1 entry when present; entries may not be `slo`, `slo_tier`, or start with `__cc_`.
- `tiers`, when set, needs ≥1 entry; each tier's `burnRate` must be `> 0` and its `longWindow` must be greater than its `shortWindow`.
- `annotations` keys starting with `everr.` are rejected: those are reserved for Everr's own generated annotations.
- Supported document kinds for apply are `Dashboard`, `AlertRule`, `Runbook`, and `SLO`.
