title: AlertRule Spec
description: The full AlertRule file format, the apply manifest, and the alert evaluation states.

An `AlertRule` is a resource with three top-level keys. Everr validates it on `everr apply` and again on read. The `spec` holds a ClickHouse query whose every returned row is a firing instance, plus the notification text to send when instances start and stop firing.

```yaml
kind: AlertRule
metadata:
  name: <slug>
spec:
  { ... }
```

| Key | Type | Notes |
| --- | --- | --- |
| `kind` | `"AlertRule"` | Selects the reconciler. Required. |
| `metadata.name` | string | The rule's **slug** and identity. Required, non-empty. |
| `spec` | object | The rule contents, below. |

## `spec`

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `evaluationInterval` | string | yes | How often the query runs. `<int><s\|m\|h\|d>`, **minimum `1m`**. |
| `for` | string | no | How long the condition must hold continuously before firing. `<int><s\|m\|h\|d>`; default `0s` (fire on the first matching evaluation). While waiting, the instance is pending and sends nothing. |
| `resolveAfter` | int | no | Consecutive empty evaluations required before a firing instance resolves. Default `1`; raise it (for example `3`) to tolerate gaps in the data. Must be ≥ 1. |
| `query` (alias `sql`) | string | yes | ClickHouse SQL. Every returned row is a firing instance; empty = resolved. **No `${...}` templating.** Set exactly one of `query` or `sql`, they are the same field: `query` is Everr's name, `sql` is the clickety-clack-native name, kept for parity with the engine's own vocabulary. |
| `notificationMessage` | object | yes | The notification text. See below. |
| `notificationMessage.title` | string | yes | Supports `${column}` (any query result column) and `${value}`. Non-empty. |
| `notificationMessage.description` | string | no | Supports `${column}` and `${value}`. |
| `instanceLabels` (alias `labelColumns`) | [string] | no | The columns that form instance identity; ≥1 entry when present. Each must be a column the query returns. Without it, all returned rows collapse into a single instance. Set at most one of `instanceLabels` or `labelColumns`, the clickety-clack-native alias for the same field. |
| `valueColumn` | string | no | A numeric result column carried onto instances and notifications as the alert's value; referenced in messages as `${value}`. Must be a column the query returns. |
| `maxInterval` | string | no | Duration string (`<int><s\|m\|h\|d>`), the ceiling for clickety-clack's adaptive evaluation backoff: the interval it may widen out to before flagging the rule degraded. When both parse, it must be greater than or equal to `evaluationInterval`. Omit it to use the engine's default. |
| `annotations` | map (string to string) | no | Free-form key/value pairs passed straight through to the clickety-clack rule alongside Everr's own generated annotations. Keys starting with `everr.`, and the exact keys `summary`, `description`, `link.alert`, and `link.runbook`, are reserved for Everr's generated sugar and rejected here. |
| `display` | object | no | `name` and/or `description`, both optional. Human-facing labels. |

A rule created directly through the engine API that carries `everr.name` and a matching `everr.repoid` is treated as owned by that repo's config: the next `everr apply` adopts it, and prunes it if no YAML file declares it.

## Message templating

`notificationMessage.title` and `notificationMessage.description` support `${...}` placeholders, substituted per firing instance when the notification is rendered:

- `${<column>}` expands to that instance's value for any column the query returns: an `instanceLabels` column resolves from the instance's labels, and every other column resolves from the event's evidence (the source row's remaining columns).
- `${value}` expands to the instance's `valueColumn` value (or, when `valueColumn` is not set, to a result column literally named `value`).

Referencing a column the query does not return is an apply-time error. `${value}` requires `spec.valueColumn` to be set unless the query returns a `value` column. A missing value renders as empty text.

Evidence is capped: an event carries at most 16 non-label columns, and only while their compact JSON stays under 4096 bytes; past the caps, refs to non-label columns may render empty (apply warns when a message depends on columns beyond the 16-column cap). The `query` SQL itself does **not** support templating, placeholders work only in the notification message fields.

## Manifest

The apply identity (the `repoid`) is inferred automatically from the repository's `origin` git remote, normalized to the slug `host/owner/repo`: scheme, credentials, port, a trailing `.git`, and trailing slashes are stripped and the result is lowercased. For example, `git@github.com:Acme/API.git` becomes `github.com/acme/api`. Equivalent ssh, https, and scp clone URLs collapse to the same identity, so one repo means one boundary.

No manifest file is needed when the repo has an `origin` remote. An optional `everr.yaml` (or `everr.yml`) at the apply root overrides the inferred identity. It accepts exactly one key:

```yaml
# everr/everr.yaml
repoid: "my-explicit-id"
```

| Field | Type | Notes |
| --- | --- | --- |
| `repoid` | string | Explicit identity override. When present it always wins over the inferred slug. Use it for local-only repositories, non-git directories, or when you need to pin an explicit name. The manifest rejects any other key. |

If there is neither an `origin` remote nor an `everr.yaml` manifest, apply errors and tells you to add a remote or create `everr.yaml`.

Declarations sit flat in `everr/`, named by kind: `*.alert.yaml`, `*.dashboard.yaml`, `*.runbook.yaml` (the legacy `*.notebook.yaml` suffix is still recognized). `everr apply ./everr` discovers every `kind: Dashboard`, `kind: AlertRule`, and `kind: Runbook` document under the directory and makes the live resources for that repoid exactly match the tree: new documents are created, changed ones updated, and removed ones **deleted**. The kind suffix is a naming convention only: apply routes by the `kind:` field. Use `--preview` to stage the changes for review without touching the live state (preview rules evaluate but never notify). See the [`everr apply` reference](/docs/reference/cli#dashboards-gitops).

## Constraints and errors

- `evaluationInterval` must be ≥ `1m`.
- `for` must be a valid duration (`0s` is allowed).
- `resolveAfter` must be an integer ≥ 1.
- `notificationMessage.title` is required and non-empty.
- `${...}` in messages must reference a column the `query` returns or be `${value}`.
- `${value}` requires `valueColumn` to be set (or a result column named `value`).
- `instanceLabels` needs ≥1 entry when present; every entry must be a column the `query` returns.
- `valueColumn` must be a column the `query` returns.
- `query` rejects `${...}`.
- Set exactly one of `query` or `sql`, never both and never neither.
- Set at most one of `instanceLabels` or `labelColumns`, never both.
- `maxInterval`, when set, must be a valid duration and, when `evaluationInterval` also parses, greater than or equal to it.
- `annotations` keys starting with `everr.`, and the exact keys `summary`, `description`, `link.alert`, and `link.runbook`, are rejected: those are reserved for Everr's own generated annotations.
- Supported document kinds for apply are `Dashboard` and `AlertRule`.
