## Question

The integrating decision: what the SDK package looks like (name, API surface, bundle budget, how packages/docs adopts it), how data travels from the browser to Everr (OTLP HTTP to the collector vs a dedicated browser ingestion endpoint; auth token model, CORS, batching, sendBeacon on unload), and how the cookieless and consented modes are expressed in the SDK API. Consult the everr-setup-telemetry skill. Needs the payload types fixed by the analytics, errors, replay, and profiling decisions.

Constraint inherited from [Decide session replay](010-session-replay-decision.md): the replay module is consent-gated and lazy-loaded only after opt-in; the dual-mode API must make "cookieless mode implies no replay" structurally true, not a runtime footgun.

Constraint inherited from [Decide browser profiling scope](012-profiling-scope.md): profiling is cut entirely, so the SDK API reserves no profiling module slot and the payload types are analytics logs, error logs, and (consented mode only) replay events.

## Resolution

1. **Ingestion for analytics and errors: the existing OTLP logs path, no new endpoint.** The SDK owns one `LoggerProvider` with a `BatchLogRecordProcessor` and OTLP/HTTP exporter on `/v1/logs`. Endpoint resolution follows the established browser pattern: public origin-bound browser key sends to `https://ingest.everr.dev/`, dev builds fall back to the local collector with no key, and a keyless production build is a structural no-op (never POSTs anywhere). Analytics and errors share the single provider, which is what makes the ticket 008 envelope stamping (one shared LogRecordProcessor) work for both signals for free.
2. **Replay transport (consented mode only): a dedicated `POST /v1/replay` route** on the same ingest host, authenticated with the same public origin-bound key. Body is a JSON batch of rrweb events tagged with `session.id` and sequence numbers; the server validates, stamps the tenant from the key, and inserts into `app.replay_events` (ClickHouse ZSTD column codec handles compression per research/005). This is the only net-new server surface in the spec, and it is built when consented mode ships, not for the homepage.
3. **Package: `@everr/otel-web` at `packages/otel-web`.** Depends on `@everr/auto-otel-errors` (error capture reused as-is per ticket 009) and `web-vitals` v5; rrweb appears only in the replay subpath.
4. **Dual-mode API: discriminated union plus mode-typed handles plus a lazy replay subpath.** `init({ mode: "cookieless" | "consented", ... })` where the cookieless options type has no replay or identity fields. `init` returns a mode-typed handle: `identify()` and replay hang off the `ConsentedClient` that only consented init returns; there are no global capability exports. Replay lives at `@everr/otel-web/replay`, dynamically imported only after consent, and `startReplay(client)` requires the `ConsentedClient` as its argument, so "cookieless implies no replay" holds three ways: zero rrweb bytes in cookieless bundles, a compile-time type error, and no runtime capability token. The SDK ships no consent banner: the host app's CMP drives the transitions, and the SDK exposes only consented init plus a `revoke()` that clears stored ids.
5. **Batching and unload delivery.** Steady state: the shared batch processor with the web app's tuning (batch size 32, 5s scheduled delay); nothing is sent per-interaction. Page exit: `forceFlush()` on `pagehide` and `visibilitychange` hidden (not `beforeunload`), riding `fetch keepalive` with `navigator.sendBeacon` fallback, final payload capped at the 64KB keepalive budget with truncation priority errors > page_leave > vitals > interaction events. Replay flushes on its own ~5s timer plus the same exit signals, sequence-numbered so ordering survives out-of-order delivery.
6. **Bundle budget: 30KB gzipped hard ceiling for the cookieless core (~25KB target), 60KB gzipped for the lazy replay chunk, enforced as a CI size gate.** The core starts on standard OTel packages (the dominant cost, ~20-25KB); if they blow the ceiling in practice, that is the trigger to revisit with a hand-rolled OTLP-JSON emitter.
7. **packages/docs adoption: mirror the web app's proven client shape.** One SSR-guarded side-effect module `src/lib/telemetry.ts` calling `init({ mode: "cookieless" })` with a docs-specific `service.name`, replacing `src/lib/posthog.ts`; endpoint/key resolution identical to `packages/app/src/telemetry/client.ts` (`VITE_EVERR_PUBLIC_INGEST_KEY`). No provider component: `PostHogProvider` disappears from `__root.tsx`, and the only React touchpoint is `captureReactError` as the router's default error component per ticket 009. The docs deployment needs its own public browser key minted with the docs origins allowlisted (origin lists are immutable, so it is separate from the web app's key). This fixes the target shape only; rollout and cutover sequencing is its own ticket.
