# Merge histogram bucket layouts on read

Status: accepted.

One histogram metric often arrives with more than one bucket layout: two services on different SDKs or versions, an SDK upgrade that changed the default bounds, or a custom view on one service. The SDKs' generic defaults (0, 5, 10, 25 up to 10000) differ from the bounds the HTTP semantic conventions advise for `http.server.request.duration` (0.005 up to 10 seconds), and SDKs adopted that advice in different versions. Counts in buckets with different edges can't be added bucket by bucket, so the Metrics page has to combine them before it computes a percentile or draws the heatmap. The first version used the series with the most observations in each interval for the whole group. When volumes were similar, that choice flipped between intervals and the p95 line jumped between distributions (about 400 ms and 1 s on the dev stack).

For each line (one group), and once for the heatmap, the bounds are chosen from every layout seen over the whole range. With one layout, it is used as is. With several, when the coarsest layout's bounds appear in all the others and its last bound is the highest of any layout, the chart uses the coarsest bounds: every count moves into a target bucket whole, so the result is exact at the coarsest resolution. Otherwise the chart uses the union of all bounds, and each bucket's count is spread over the union buckets it overlaps in proportion to width; observations above a series' last bound go to the union bucket just above it. Bounds are chosen once per group for the range, so a line's resolution doesn't change between intervals. Average and rate come from `Count` and `Sum`, which add exactly, and are unaffected. A note under the chart says how many layouts were combined and whether the result is exact or estimated, and the heatmap tooltip marks interpolated counts as `≈ n`. The code is `bucketLayout` and `rebucket` in `packages/telemetry-explorer/src/metrics/data/histogram.ts`.

No other platform picks one series per interval. Those that keep exact bucket counts merge only where bounds line up: Prometheus native histograms reduce exponential schemas to the coarsest one, and custom-bucket histograms keep only the boundaries they share. Those that accept any layout re-bucket into one representation at ingest, which is an approximation: Elastic converts explicit bounds to its exponential histogram (T-Digest before 9.4), and Datadog converted OTLP histograms to DDSketch. Everr stores the raw explicit bounds and queries on read, so it can't normalize at ingest, but choosing per query lets it be exact when that costs nothing. Shared bounds alone can collapse to a few buckets, or only the overflow bucket, when layouts don't nest, as with SDK defaults next to the semantic convention bounds; that is the common case, so it can't be the only method. Interpolating inside a bucket assumes observations are spread evenly within it, which `bucketQuantile` already assumes to place a percentile inside its bucket, as `histogram_quantile` does, so the estimate adds little new error.

The exact path requires that one layout nest in all the others, not that "enough" bounds are shared, so there is no threshold to choose and defend: nesting is exactly the case where shared bounds lose nothing beyond the coarsest input's resolution. It also requires the shared bounds to reach every layout's highest bound, because a percentile above the last bound reports that bound. On the dev stack, one service's 4 bounds (up to 0.5 s) nested inside another's 6 (up to 2.5 s); on the shared bounds, p95 was capped at 500 ms during a slowdown while exemplars showed 2 s requests, and on the union it read about 860 ms. Exact but capped is worse than estimated but uncapped, so the exact path only gives up resolution, never range.

Revisit if a real tenant shows estimates that mislead, for example a coarse layout of a few wide buckets spread over a fine one, where the even-spread assumption is weakest; a line per bucket layout would then be the honest view. Exponential histograms already merge exactly by reducing scale, so converting explicit-bounds series to them, as Elastic does, is an alternative to interpolation. Grouping by `service.name` avoids the merge in the common case, and a hint pointing to it from the note could be enough.
